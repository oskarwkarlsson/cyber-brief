"SignDrop": unpatched Windows zero-day with public exploit gives SYSTEM and can disable antivirus and EDR self-defense

Researcher Abdelhamid Naceri (Nightmare Eclipse) released a proof-of-concept that abuses the CLFS authentication mitigation Microsoft added in October 2025: by forcing a privileged process such as Windows Defender to open a log file, the ".cnpf" authentication file gets created with SYSTEM rights. He says the same trick passes antimalware tamper protection because the file write appears to come from the engine's own process. Tested on Windows 11 26H2 and Windows Server 2025 Experimental; his estimate that 80% of Windows installs are vulnerable is his own. A machine is exposed if HKLM\SYSTEM\CurrentControlSet\Services\CLFS\Authentication\Mode is 0 or 1. No Microsoft fix or statement yet, and disabling the mitigation would reopen CLFS memory-corruption attacks. Not reported as exploited in the wild, but the code is public. Takeaway: a local privilege escalation, so treat it as a post-compromise accelerant; hunt for unexpected .cnpf file creation and watch for Microsoft guidance.

PHP2Shell on Check Point gateways: a new root escalation, a backdoor, and a wiper against Israeli organizations

Check Point Research says that from 30 October, about a week after a fix was out, an attacker hit unpatched Security Gateways through Mobile Access portals with PHP2Shell, then escalated to root with a newly tracked DynamicCLI flaw, CVE-2026-123039. It deployed PHP webshells and the TSGA backdoor with a TSProxy component, pivoted over SSH to VMware ESXi hosts and ran a "destroy_v6" wiper with DREAM_ANNEXATION.txt notes in the first wave against Israeli organizations. A broader second wave on 2 November hit several countries without destruction. TSGA and TSProxy are variants of PhiliKit, which ESET tied to China-nexus UNC5221, but Check Point says it cannot attribute with confidence and lists access broker or false flag as possibilities. Takeaway: if your Check Point Mobile Access portal was unpatched around late October, assume compromise is possible, hunt for TSGA and webshells, and check ESXi hosts reachable from the gateway.

AI/Cloud

Autonomous AI attacks are now routine for spies: Unit 42's "Cairn" operations and CloudSEK's Silent Lynx agent server

Unit 42 says Chinese-speaking attackers (tracked as CL-STA-1238, moderate confidence China-nexus) used the open-source AI pentest framework Cairn with Zhipu GLM and DeepSeek models to run 25 largely autonomous operations against at least 19 organizations in August and September, succeeding at 10: valid credentials, over a million personal records at one victim, military and government identities, persistent admin accounts, and an edited live industry standards ballot. Targets included advanced semiconductor makers, US defense policy and civil society. Separately, CloudSEK found an exposed server of the suspected Kazakhstan-linked Silent Lynx group showing an operator steering the open-source Hermes agent (mostly DeepSeek models) over Telegram for reconnaissance, collection and log wiping, with months of access to Tajikistan's national railway and government document platform, per The Record. Takeaway: expect faster, noisier, machine-driven intrusion attempts; rate limits, anomaly detection on credential use and fast patching of exposed services matter more than ever.

ConnectWise: the ScreenConnect MSP breaches trace to the third-party RMM+ extension, found in about 400 partner environments

ConnectWise says the activity behind the nearly 50 breached organizations appears to stem from abuse of RMM+, an independent extension that exposes a passphrase-protected API able to run remote commands. It has disabled RMM+ in the roughly 400 cloud partner environments where it was installed, stresses that presence alone does not mean compromise, and says on-prem customers must disable it themselves. Attackers deployed extra remote-access tools and may have compromised technician workstations during interactive sessions. ConnectWise warns that disabling the extension and resetting credentials may not remove persistence already planted. Takeaway: every ScreenConnect customer should confirm RMM+ is off, then hunt endpoints and technician machines for added remote-access software.
